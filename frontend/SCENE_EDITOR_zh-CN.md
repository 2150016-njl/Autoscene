# AutoScene 1.3.1 场景编辑、显示与逐车算法

本次更新针对 `frontend/` 源码；已有的旧版 deb 安装包不会自动更新。

## 实车位置与方向

加载数据后，主车、橙色实车候选/已绑定实车、绿色 virtual BV 都可以拖动车身修改位置。
选中车后，拖动蓝色手柄修改朝向；也可以在地图上方选择车辆，直接输入 x、y 和朝向。
地图与输入框的 x/y 使用数据集全局米制坐标，朝向框使用度；发送 ROS 时仍转换为原有的局部坐标和弧度。

这里修改的是实验的初始位置配置，不是让物理车辆立即开到鼠标位置。
处于准备、启动、运行或停止过程时，车辆编辑会锁定。

## nuPlan 放置

1. 从“选择车辆 / 放置源”中明确选择一台未绑定的周车，也可以直接点地图上的那台车。
2. 点击“放置 virtual BV”，然后点目标位置。
3. 默认严格使用点击位置，不自动选择最近的另一台车，也不退回周车历史轨迹。
4. 如需对齐道路，勾选“放置时吸附车道”。没有真实车道或距离车道超过 8 米时会拒绝放置并提示。

选中的源轨迹只对应一个图元；转为 virtual BV 后不会再在原处画一台重复车辆。
nuPlan 只显示当前帧有效的对象，不会把过去或未来才出现的车辆拉到当前帧。

针对“启动仿真后跳到周车位置”，还修复了运行侧的预测身份对应问题：
Pluto 批量预测的补齐行不再被当成真实周车，目标 ID 优先完整匹配，歧义短后缀不会
任意匹配到第一辆车。特征构造时请求的车辆与实际主对象不一致会直接报错，避免把
主车轨迹贴给其他车辆。上述情况有 CPU 回归用例；具体异常场景仍需用原算法组合复测。

另一个已确认的设置冲突：`history_source=dataset` 不采用界面编辑的 `initial` 位姿，
启动时仍会读取 PKL 轨迹。现在若预览中的车辆位置/朝向与原文件不同，会在提交参数或
启动前拒绝继续并说明原因。请切换到 `initial`，或另存新 PKL、加载导出目录后再准备。
这不会自动切换历史来源，也不会擅自改写原数据。

运行侧也取消了以 track 名称猜测 MetaDrive 对象的后备逻辑：未激活轨迹显示为无效，
初始化与平台镜像只操作明确映射的车辆；有效平台反馈缺少映射时会报错，且在移动任何
车辆前先检查这一批反馈的全部映射。这是身份保护，不代表已经复现并定位你的异常场景。

## 字体与窗口

- 顶部第二行直接显示“界面字号”，旁边有“A− 缩小 / A+ 放大”。支持 100%–200%，默认 125%，重启后保留。
- 右下角也保留同步入口；不需要拉到窗口底部才能调字。
- `Ctrl+=` / `Ctrl+-` 调整字号，`Ctrl+0` 恢复默认。
- `F8` / `F9` 隐藏或显示左右侧栏；菜单“显示”也提供入口。
- 最大化或还原窗口不会重置字号。地图缩放与界面字号分开控制。
- 小窗口或大字号时，工具栏超出的操作可通过末端展开入口访问，表格和侧栏可滚动。

## 从已有 PKL 构建新场景

仅打开你信任来源的 PKL 文件；Python pickle 不是安全的陌生文件交换格式。

1. 加载原数据目录，选择场景；也可以点击“打开 PKL…”选择单个场景文件。
2. 勾选“场景构建（含背景车）”，此时背景车辆也可以选中、拖动或旋转。
3. 完成调整后点击“另存新 PKL 场景…”，输入一个尚不存在的新目录名。
4. 导出目录包含 `sd_ui_variant_*.pkl`、`dataset_summary.pkl`、`dataset_mapping.pkl`。
5. 在左侧加载新目录，查看保存后的场景；在 ROS 主机使用时也要复制这个新数据集。

保存会以显示帧为锚点，对所编辑车辆的整段有效轨迹做平移/旋转，同时旋转速度向量和航向。
地图、未编辑车辆、有效帧掩码、时间戳和原始文件保留。目标目录已存在时会拒绝覆盖。
virtual BV 的位置编辑应用到其绑定的原始 track，当前版本不会凭空生成一条新车辆轨迹。

这是一版基于已有轨迹的场景变体编辑器，不会自动规划另一条道路路线，也不会自动保证
修改后的轨迹始终在道路内、无碰撞。速度设置仍用于实验初始条件，不会在导出时重写整段速度曲线。
构建模式下暂停实验配置提交，避免将尚未导出的背景车编辑误当成 ROS 已采用的配置。

## 每辆车选择算法

1. 在“场景可视化”地图下方，实车/virtual BV 表格的车名旁直接选择“算法”。
   或者在地图上方选择 EGO / 已配置车辆，再选择“该车算法”。
   顶部“逐车选择算法…”和“车辆算法”页签也保留，所有入口相互同步。
2. 每辆车可选 `默认`、`Pluto`、`VBD`、`Pluto Hybrid`。
   默认表示不指定单车覆盖，继承后端的主车 / 周车默认算法，不代表停止或回放。
3. 未绑定实车候选可以预选算法，绑定后才参与运行；未配置背景车继续使用数据集回放。
4. 点击“保存 YAML”保存配置；“准备 BV”写入 ROS，随后“启动实验”创建实际算法调度。
   改算法后旧的准备状态失效，运行期间不能修改算法。

主车选择写入 `ego.planner_method`，周车/实车选择写入对应的 `vehicles.agents[].planner_method`。
前端和 ROS 主机的后端都需要更新；仅替换前端不能让旧后端获得逐车调度能力。
例如：

```yaml
ego:
  planner_method: Pluto
vehicles:
  agents:
    - id: agent_001
      scenario_track_id: adv_1
      platform_id: platform_001
      planner_method: VBD
    - id: agent_101
      scenario_track_id: adv_2
      platform_id: -1
      planner_method: pluto_hybrid
```

“沿用默认算法”不写逐车覆盖，使用后端的主车/周车默认设置。
逐车覆盖优先于 `/algorithm` 的 `ego_method/adv_method`，再回退到生成器 YAML。
`planner_mode=max` 是候选轨迹选择方式，不是算法名。

同算法车辆合批推理；VBD 主车和 VBD 周车共用一份联合预测，其他车辆不会执行 VBD 给它们的预测。
每组采用自身的中心/后轴参考转换，轨迹输出也按对应车辆的算法转换。
实车规划仍通过原平台接口下发，真实状态以反馈为准，不由规划轨迹擅自覆盖。
原有约束仍保留：实车 hybrid 使用 TJ-West；`initial_once` 是固定轨迹模式，若要逐车模型规划
必须在配置中使用 `platform.trajectory_mode=pluto_replan`，否则拒绝显式算法选择。

## VBD 后端调度

不再提供 UI 频次旋钮。后端默认开启 `vbd_adaptive_cadence` 与 `vbd_async_prefetch`：
从 10 仿真帧间隔开始，根据实测耗时调整，并在旧预测到期前后台计算下一份预测。
只有一个 VBD 模型和一个工作线程；请求使用独立场景快照，不与仿真修改的数组共享写入。

控制循环继续按时间截取 80 点预测中的有效 50 点；新结果也按采样时间推进，不从第 0 点重新播放。
首次预测、重置或换场景可能需要等待；正常刷新不在控制线程等待扩散推理。
若 GPU 过慢导致有效预测用尽，会报错，不会无限沿用旧轨迹或伪造尾点。
这减少了 VBD 对控制线程的周期性阻塞，但不保证其他算法、渲染、网络或所有硬件都没有卡顿。

模型采样步数和权重没有更改。需要部署到实际 ROS/GPU 主机并重启后端，旧后端不会识别新的逐车调度。
技术细节和测试范围见后端 `unitraj/closeloop/VBD/SCHEDULING.md`。
